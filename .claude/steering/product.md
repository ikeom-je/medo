## 1. サービス概要・核心メッセージ

### 核心メッセージ

> **アイデアから「目処が立つ」までを最速にする。**
> 発想は自由に、事実は縛る。

### 一文で何のサービスか

サービスやアプリのアイデア・ヒアリング内容を対話で要件に育てながら、鮮度保証付きのGoogle Cloudナリッジに基づいて、複数のアーキテクチャ案・コスト試算・MVPモック・提案スライドを高速に生成する**上流工程Agentケイパビリティ(Agent + Skill + CLI)**。

### 名前の由来

| 表記 | 役割 |
|---|---|
| 目処(Medo) | 「目処が立つ」= 意思決定の見通しを高速に立てる、という価値そのもの |
| medo | CLIコマンド名・パッケージ名・英字ブランド |

---

## 2. ターゲットユーザー

- **本人(個人利用)**: 自分および顧客のサービス/アプリのGCPアーキテクチャを検討・提案する立場。認証・マルチテナントなし
- **将来**: 所属チーム(蓄積された要件・業界ナリッジを共有)

---

## 3. 解決する課題

1. アイデア段階の曖昧な入力から要件を引き出す作業が毎回手作業で、成果が案件ごとに使い捨てになる
2. AI/ML系サービスの更新が速すぎて、LLMの学習知識では「今なら解決できるようになったこと」を見落とす
3. 新機能のPreview/GA・安定性・事例有無という「判断に効くメタ情報」が単発プロンプトでは取れない
4. 提案がプロンプト次第・実行ごとに揺れて、比較検討や意思決定の土台にならない
5. 顧客に見せられる形(動くモック・スライド)にするまでが遠く、提案・意思決定が遅い

**成功の姿**: アイデアを話してから半日以内に「動くモック+根拠付きアーキ比較スライド」を顧客に見せられる。

## 4. 設計原則

### 原則1: 発想は自由、事実は縛る

アーキ案・スライドの文章は創造的な生成物だが、引用するサービス情報・launch_stage・料金は必ずCLIツールが返すカタログ値・SKU計算値を使う。数値・ステータスの通り道にLLMを挟まない。

### 原則2: 役割の三分担

| 役割 | 担当 | 決定論性 |
|---|---|---|
| 手順(ヒアリング・提案の進め方) | Skill(ホストLLMが実行) | 生成的 |
| 事実と計算(カタログ・料金・要件保存) | medo CLI + core | 決定論 |
| かさばる検索の圧縮 | 内蔵Gemini Flash(knowledge-digest) | 生成的だが出典必須 |

### 原則3: 要件は最初から確定しない

要件ドキュメントはバージョン付きの「生きた成果物」であり、ハブ。各生成物はその時点の要件バージョンに紐づく。アーキ案を見て過不足に気づいたら、どの段階からでも要件に戻って更新→陳腐化した生成物を機械的に検出して再生成できる。`confidence`(confirmed/assumed/open)と`open_questions`がこの原則の実装。

### 原則4: 鮮度契約

カタログエントリは出典URL・`last_verified`必須。30日超過で`stale: true`が全レスポンスに付き、Skillは提案文中への注記が義務。金額はカタログに焼き込まず、SKU参照から都度計算する。

### 原則5: 失敗を推測で補完しない

CLI失敗時は非ゼロ終了+構造化エラー。Skill側も「推測で補完せず失敗を報告する」契約を持つ。ETLはバリデーション通過分のみコミットする。

## 5. 差別化軸(何をやらない)

| 軸 | やらない | やる |
|---|---|---|
| エージェント構成 | 自律的なmulti-agent(非決定性が増える) | 会話Agent(1体)+決定論的ツール群 |
| 知識の持ち方 | LLMの学習知識・その場の検索一発生成 | 鮮度メタ付きカタログ+出典必須 |
| 提供形態 | 単一のWebアプリに閉じる | Skill+CLIの可搬なケイパビリティ層(Claude Code / agy両対応) |
| MCPサーバー | 最初から作る(コンテキスト肥大) | シェルなしホストが必要になったら薄いアダプタとして追加 |
| モック生成 | コーディング支援・実装が目的 | 合意形成(意思決定の高速化)が目的 |
| ドキュメント検索 | 自前で再発明 | 公式Knowledge MCP等を素材として利用 |
| スライド生成 | コアの固定機能 | ホストLLMが対話的に作るSkill(Claude/Gemini比較可能、`generated_by`記録) |
