## 1. サービス概要・核心メッセージ

### 核心メッセージ

> **ビジネスの打ち手に「目処」をつける。**
> 発想は自由に、事実は縛る。

### 一文で何のサービスか

業界・ビジネス状況・経営思想のヒアリングから始め、出典付きの市場・国策・業界動向データとフェルミ推定に裏づけられた打ち手候補をミニPRFAQとして比較提示してWhat/Whyの合意を最速でつくり、合意案を鮮度保証付きGoogle Cloudナリッジに基づく完全版PRFAQ(How+効果)に育てる**上流工程Agentケイパビリティ(Agent + Skill + CLI)**。

### 名前の由来

| 表記 | 役割 |
|---|---|
| 目処(Medo) | 「目処が立つ」= 意思決定の見通しを高速に立てる、という価値そのもの |
| medo | CLIコマンド名・パッケージ名・英字ブランド |

---

## 2. ターゲットユーザー

- **本人(個人利用)**: 自分および顧客のビジネス課題を整理し、打ち手とGCPアーキテクチャを検討・提案する立場。認証・マルチテナントなし
- **将来**: 所属チーム(蓄積された課題・方針・要件・業界ナリッジを共有)

---

## 3. 解決する課題

1. What/Whyの合意がないままHow(システム要件・アーキ検討)に突入し、後戻りが起きる
2. 市場・国策・業界動向を踏まえた打ち手の比較検討が毎回手作業で、提案の説得力が個人の経験と勘に依存する
3. アイデア段階の曖昧な入力から課題・要件を引き出す作業が毎回手作業で、成果が案件ごとに使い捨てになる
4. AI/ML系サービスの更新が速すぎて、LLMの学習知識では「今なら解決できるようになったこと」を見落とす
5. 新機能のPreview/GA・安定性・事例有無という「判断に効くメタ情報」が単発プロンプトでは取れない
6. 提案がプロンプト次第・実行ごとに揺れて、比較検討や意思決定の土台にならない
7. 顧客に見せられる形(PRFAQ・スライド・動くモック)にするまでが遠く、提案・意思決定が遅い

**成功の姿**: 課題を話してから半日以内に、市場・国策・業界動向データとフェルミ推定に裏づけられた打ち手のミニPRFAQ比較でWhat/Whyに合意し、合意案の完全版PRFAQ(技術的背景・workflow改善見込み・効果・ロードマップ)まで持ち帰れる。

## 4. 設計原則

### 原則1: 発想は自由、事実は縛る

打ち手の発想・PRFAQ・スライドの文章は創造的な生成物だが、引用する市場数値・国策・業界動向・サービス情報・launch_stage・料金は必ずCLIが検証・保存した出典付きファクトとカタログ値を使う。保存後の数値の通り道にLLMを挟まない — **フェルミ推定の計算もコード(fermi計算機)が行う**。LLMが数値に触れるのは出典からの初回転記のみ(出典に忠実・無加工。換算・集計はfermiで行う)。

### 原則2: 役割の三分担

| 役割 | 担当 | 決定論性 |
|---|---|---|
| 手順(ヒアリング・打ち手提案・PRFAQ育成の進め方) | Skill(ホストLLMが実行) | 生成的 |
| 事実と計算(ファクト保存検証・フェルミ計算・カタログ・料金・要件保存) | medo CLI + core | 決定論 |
| かさばる検索(市場・国策・業界動向) | ホストLLMの検索 +(フェーズ2)内蔵digest | 生成的だが出典必須 |

### 原則3: 課題も要件も最初から確定しない

要件ドキュメント(背景・方針/理念・課題・要件)はバージョン付きの「生きた成果物」であり、ハブ。各生成物はその時点の要件バージョンに紐づく。打ち手の比較やQ&Aで過不足に気づいたら、どの段階からでも戻って更新→陳腐化した生成物を機械的に検出して再生成できる。`confidence`(confirmed/assumed/open)と`open_questions`がこの原則の実装。**方針・理念(principles)は検索で取れる事実ではなく、ヒアリングとブレストで引き出して合意する対象**で、打ち手の評価軸になる。

### 原則4: 鮮度契約

GCPカタログエントリは出典URL・`last_verified`必須(30日超過でstale)、市場ファクトは`source`・`retrieved`必須(180日超過でstale)。staleは全レスポンスに付与され、Skillは提案文中への注記が義務。金額はカタログに焼き込まず、SKU参照から都度計算する。

### 原則5: 失敗を推測で補完しない

CLI失敗時は非ゼロ終了+構造化エラー。出典のないファクトはバリデーション拒否。フェルミ計算は未定義変数・許可外演算をエラーにする。Skill側も「推測で補完せず失敗を報告する」契約を持つ。ETLはバリデーション通過分のみコミットする。

## 5. 差別化軸(何をやらない)

| 軸 | やらない | やる |
|---|---|---|
| 提案の階層 | Howだけの提案(アーキ図の一発生成) | What/Whyの合意形成を主戦場に、Howは事実に縛った裏付けとして添える |
| リサーチ | 網羅的な市場調査レポートの自動生成 | 案件に必要な範囲の出典付きファクト+フェルミ推定で「意思決定の桁感」を最速で揃える |
| エージェント構成 | 自律的なmulti-agent(非決定性が増える) | 会話Agent(1体)+決定論的ツール群 |
| 知識の持ち方 | LLMの学習知識・その場の検索一発生成 | 鮮度メタ付きカタログ+出典必須ファクト |
| 提供形態 | 単一のWebアプリに閉じる | Skill+CLIの可搬なケイパビリティ層(Claude Code / agy両対応) |
| MCPサーバー | 最初から作る(コンテキスト肥大) | シェルなしホストが必要になったら薄いアダプタとして追加 |
| モック生成 | コーディング支援・実装が目的 | 合意形成(意思決定の高速化)が目的 |
| ドキュメント検索 | 自前で再発明 | 公式Knowledge MCP等を素材として利用 |
| スライド生成 | コアの固定機能 | ホストLLMが対話的に作るSkill(Claude/Gemini比較可能、`generated_by`記録) |
