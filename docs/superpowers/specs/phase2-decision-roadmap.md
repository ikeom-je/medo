# decision-roadmap: 次に潰すべき不確実性(フェーズ2・後続)

ステータス: 未承認(実装着手前)

未確定事項(`open_questions`)と未検証の仮説(`hypotheses`)のうち、**どれを先に確かめると、どの策を取るかが最も決まるか**を並べる設計。1つ決まると他も決まる**決め手の仮説**を見つけ、策の選択を分ける**重要なパラメタ**を特定し、策を**2〜3通り(メインとサブ、3つなら松竹梅)**用意して、**どの値を境に策が切り替わるか**を計算する。確かめる中身を「その値は X 以上か」に絞って追い込む。

親: [medo-phase2-design.md](medo-phase2-design.md)(「後続」の `decision-roadmap`)。関連: [ドメインモデル](phase2-domain-model.md) / [status契約](phase2-status-contract.md) / [生成物のライフサイクル](phase2-artifact-lifecycle.md) / [knowledge-digest](phase2-knowledge-digest.md)(Jevの使い方を揃える)

---

## 1. なぜ要るか

元の構想(`medo-design.md` §5)は「open_questions を不確定パラメタとした修正コントロール」の1行だけで、詳細が無い。

案件が進むと未確定事項と仮説は増えるが、**どれから確かめるべきか**を示す仕組みが無い。`status` の `actions` は「未確認のチェック項目がある」は示すが、「どの不確実性を潰すと判断が動くか」は示さない。すべてを等しく確かめに行くと時間がかかり、判断に効かない項目に手間をかける。

また、打ち手を1つに絞ったまま進めると、決め手の仮説が外れたときに代わりが無い。**策は最初から複数用意し、不確実性の結果に応じて切り替える**のが前提である。

### 用途と範囲

- 社内向けの判断材料。顧客に見せるロードマップ(最終提案スライドの第6章)の素材にはなり得るが、本設計の目的ではない
- 出力は**呼ぶたびに計算するビュー**(`status --view uncertainty`)。版を固定して保存する生成物にはしない。優先順位は要件や仮説の状態が変わるたびに変わる計算結果であり、保存すると陳腐化の管理が要るため。**生成物の型を新設するか `comparison` を使うか**という未決事項(medo-phase2-design.md §6-3)の答えは「どちらでもない」とする

## 2. 方式の選択

| 案 | 内容 | 判断 |
|---|---|---|
| **A(採用)** | 決定論の結びつき + fermi による感度・切り替え点の計算 + Jev の分類で並べるビュー | 計算できる部分(数値の振れ)はコードが計算し、計算できない意味の判断だけを Jev に任せる。knowledge-digest と同じ分担 |
| B | ホストLLMが優先順位を書き、生成物として保存する | 順位がモデルや実行のたびに揺れる(product.md 課題6)。要件が変わるたびに作り直しが要る |
| C | 決定論だけ(結びつく課題・打ち手の数で並べる) | 「解消したら判断が変わるか」という意味の判断ができず、結びつきの多い項目が上に来るだけになる |

## 3. 考え方: 決め手・重要なパラメタ・策の切り替え

### 3.1 決め手の仮説(1つ決まると他が決まる)

未確定事項と未検証の仮説(`status` が `unvalidated` / `validating`)を節点、「A が確定すると B も決まる、または大きく絞られる」を有向の辺とするグラフを作る。

- **候補の組**(決定論): 同じ fermi 推定の変数に結びつく(仮説の `fermi_ref` が同じ推定を指す)/ 同じ課題を根拠にしている(`challenge_ids` が重なる)/ 未確定事項の範囲(`scope`)が同じ課題を指す。全組み合わせは聞かない
- **辺**: 候補の組について、向きごとに Jev の `implies`(§5)を聞き、確率が閾値以上なら辺を張る
- **波及範囲**: 節点から辺をたどって到達できる節点の数。大きいほど決め手である

### 3.2 重要なパラメタ(感度)

fermi 推定の仮定の変数(`assume`)を1つずつ動かしたとき、推定値がどれだけ振れるかを計算する(トルネード図と同じ考え方)。ファクト参照の変数(`fact`)は動かさない(出典に縛られた値であり、不確実性の対象ではない)。

- 動かす幅: 各変数の仮定値の 1/2 倍〜2 倍
- 振れ幅 = その範囲での推定値の最大と最小の差。推定値に対する比も返す
- **同じ変数名が複数の策の推定に現れるとき**、その変数を「策の選択を分ける共通のパラメタ」として優先する

### 3.3 策を2〜3つ並べ、切り替わる点を求める

1つの判断に対して、策を**最低2つ、最大3つ**用意する(メインとサブ。3つなら松・竹・梅)。各策はそれぞれ fermi の推定を持つ(同じ式で仮定の値の組が違う場合も、別の式の場合もある)。

- 共通のパラメタを動かしたとき、**どの策の推定値が上になるかが入れ替わる値(切り替え点)**を逆算する。例: 「利用率が30%以上なら松、15〜30%なら竹、15%未満なら梅」
- 確かめるべき問いは「利用率は30%以上か、15%以上か」の2点に絞られる。値を正確に突き止めなくても、どの区間にあるかが分かれば進む策が決まる
- 推定値は「大きいほど良い」とする(効果・売上など)。費用のように小さいほど良い推定は、策の fermi の側で効果から費用を引いた形に書く。向きを推定ごとに持たせると比較の規則が分岐するため、v1 では持たせない

**判断の境目**は策どうしの比較を優先する(外から与える必要が無い)。加えて、KPI の目標値(`kpis[].target_value`)との比較もできる(「最低限ここを超えるか」の確認)。KPI と推定の単位が一致しない場合は比較しない。

## 4. スキーマ

### 4.1 策の役割と推定(mini-prfaq の `OptionMeta`)

**新しい生成物の型は作らず、既存の `mini-prfaq`(打ち手の候補セット)に乗せる。** もともと2〜3案の候補を並べる生成物である。

```python
class OptionMeta(BaseModel):
    name: str
    approach_type: str = ""
    tier: Literal["", "main", "sub", "matsu", "take", "ume"] = ""
    fermi: str = ""            # その策の推定(fermi-vN)
```

- CLI の入力は既存の `--options "名前:手法の型"` を `"名前:手法の型:tier:fermi-vN"` に広げる(後ろ2つは省略可)。既存の書式はそのまま受ける
- **新規に保存する mini-prfaq は、策が2つ未満または3つより多ければ拒否する**(最低2つ・最大3つを CLI が強制)。既存の保存データは読み込みで検査しない
- tier の組は `main` 1つ + `sub` 1〜2つ、または `matsu` / `take` / `ume` を各1つ、のどちらか。混ぜたら拒否する。tier を1つも付けない策のセットは受ける(切り替え点の計算対象外)
- `fermi` は同じ案件に存在する `fermi-vN` でなければ拒否する

### 4.2 既存のスキーマとの関係

- 仮説の `fermi_ref`(`artifact_id` + `variable_name`)はそのまま使う。同じ変数名が複数の策の推定に現れれば共通のパラメタとみなす(§3.2)
- `FermiModel` は変えない。感度と切り替え点は既存の `evaluate` を仮定値を差し替えて繰り返し呼んで求める

## 5. Jevに聞くこと

数値には触れず、関係と性質の分類だけを聞く(原則1)。

| 質問 | 型 | 対象 | 目的 |
|---|---|---|---|
| `implies` | noul | §3.1 の候補の組(向きごと) | 「A が確定すると B も決まる、または大きく絞られるか」。決め手を見つける辺 |
| `decision_relevant` | noul | fermi に結びつかない項目 | 「これが解消したら、どの策を取るかが変わり得るか」。切り替え点を計算できない項目の重み |
| `effort` | choice | すべての項目 | 確かめる手間(`ask` すぐ聞ける / `research` 調査が要る / `experiment` 実証が要る) |

`state` には、項目の本文、結びつく課題・策の名前と tier を渡す。`implies` の閾値は評価セットで決める(出発点 0.8)。

## 6. 並べ方と出力

### 6.1 並べ方(決定論)

重みづけの足し算はせず、上から順に比べる(重みの値そのものが根拠のない数値になるため)。

1. 波及範囲が大きい
2. 切り替え点を持つ(確かめれば策が決まる)
3. `decision_relevant` が 0.5 以上
4. 手間が小さい(`ask` < `research` < `experiment`)

### 6.2 出力 `medo status --view uncertainty`

各項目は次を持つ。json と digest の両方を返す。

| フィールド | 内容 |
|---|---|
| `id` / `kind` | 項目のID(`oq-N` / `hyp-N`)と種類 |
| `keystone` | 波及範囲と、辺の根拠(決定論の結びつき・`implies` の確率) |
| `parameter` | 結びつく共通のパラメタと、各策での振れ幅 |
| `options` | 策ごとの名前・tier・推定値(仮定値のまま) |
| `switch_points` | 切り替え点(どの値を境にどの策が上になるか)。無ければ理由 |
| `ask` | 確かめるべき問い(「<変数> は <値> 以上か」) |
| `effort` / `decision_relevant` | Jev の分類 |

### 6.3 計算できない場合

推測で補わず、理由と一緒に返す。

| 状況 | 扱い |
|---|---|
| mini-prfaq が無い、または策に fermi が無い | `switch_points` は空、理由「策に fermi が無い」。Skill は fermi を足すよう促す |
| 共通のパラメタが無い(策ごとに別の変数) | 切り替え点は計算しない。理由「策の選択を分ける共通の変数が無い」 |
| 範囲内に切り替え点が無い | 「調べた範囲の全域で <策> が上」。そのパラメタは決め手ではない |
| 推定の計算が失敗する(0除算など)点がある | その点を除いて探索し、除いた範囲を理由に含める |

**切り替え点の探し方**: 各策の仮定値の 1/10 倍〜10 倍の範囲を対数刻みで200点に区切り、順位が入れ替わる区間を二分法で詰める(相対誤差 1e-6 まで)。式が単調でなくても、入れ替わる点をすべて返す。

### 6.4 Jevが使えないとき

既存の `research triage` / `knowledge dedupe` とそろえる。

- `TYPESAFE_API_KEY` が無い: 決定論の部分(感度・切り替え点・決定論の結びつきだけでの波及範囲)を `judge: unavailable` 付きで返す(終了コード0)
- 鍵があるのに呼び出し・解析が失敗した: 非ゼロ終了し `error:` を出す

## 7. Skill

- `medo-propose-options`: 策を**最低2つ・最大3つ**作り、メインとサブ(3つなら松竹梅)の tier と、策ごとの fermi を付けて保存する。fermi は策ごとに `medo fermi calc` で作り、仮定には根拠のメモを付ける
- `medo-decide`: 振り返りで `medo status --project <id> --view uncertainty` を読み、最上位の「確かめるべき問い」を次の周回の焦点(`focus_hypothesis`)の候補としてユーザーに示す。80行の上限内に収める

## 9. テストと評価

- 決定論のユニットテスト: 感度、切り替え点(単調な式・単調でない式・入れ替わりが無い・計算失敗点を含む)、波及範囲、並べ方、策が2〜3つかと tier の組の検査、既存 mini-prfaq の読み込み
- Jev は既存のテストと同じく差し替える。鍵なしで `judge: unavailable`、失敗で非ゼロ終了
- **正解付きの評価セット**(`scripts/eval/` に置く): `implies` の組(決まる・決まらないの正解付き)を、調整用と検証用に分ける。受け入れ条件は検証用の組で、誤って辺を張る率が1割以下、正しい辺の8割以上を拾う(評価前に固定)

## 11. やらないこと

- **生成物として保存する**: 呼ぶたびに計算する(§1)
- **重みの足し算による総合点**: 根拠のない重みを作らない(§6.1)
- **ファクト参照の変数を動かす**: 出典に縛られた値は不確実性の対象にしない
- **推定ごとの良し悪しの向き**: v1 は「大きいほど良い」に揃える(§3.3)
- **策が4つ以上**: 比べる軸が増えて追い込めなくなる。最大3つ(松竹梅)
- **顧客向けロードマップの生成**: 最終提案スライドの第6章の素材にはなり得るが、本設計では扱わない
