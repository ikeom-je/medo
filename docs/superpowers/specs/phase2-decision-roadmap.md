# decision-roadmap: 次に潰すべき不確実性(フェーズ2・後続)

ステータス: 承認済み(2026-10-05、相互レビュー Codex+agy 2R。運用で課題が出たら改訂する前提)

未確定事項(`open_questions`)と未検証の仮説(`hypotheses`)のうち、**どれを先に確かめると、どの策を取るかが最も決まるか**を並べる設計。1つ決まると他も決まる**決め手の仮説**を見つけ、策の選択を分ける**パラメタ**を明示し、策を**2〜3通り(メインとサブ、3つなら松竹梅)**用意して、**どの値を境に策が切り替わるか**を計算する。確かめる中身を「(他の仮定が今のままなら)その値は X 以上か」に絞って追い込む。

親: [medo-phase2-design.md](medo-phase2-design.md)(「後続」の `decision-roadmap`)。関連: [ドメインモデル](phase2-domain-model.md) / [status契約](phase2-status-contract.md) / [生成物のライフサイクル](phase2-artifact-lifecycle.md) / [knowledge-digest](phase2-knowledge-digest.md)(Jevの使い方を揃える)

---

## 1. なぜ要るか

元の構想(`medo-design.md` §5)は「open_questions を不確定パラメタとした修正コントロール」の1行だけで、詳細が無い。

案件が進むと未確定事項と仮説は増えるが、**どれから確かめるべきか**を示す仕組みが無い。`status` の `actions` は「未確認のチェック項目がある」は示すが、「どの不確実性を潰すと判断が動くか」は示さない。すべてを等しく確かめに行くと、判断に効かない項目に手間をかける。

また、打ち手を1つに絞ったまま進めると、決め手の仮説が外れたときに代わりが無い。**策は最初から複数(最低2つ、最大3つ)用意し、不確実性の結果に応じて切り替える**のが前提である。

### 用途と範囲

- 社内向けの判断材料。顧客に見せるロードマップ(最終提案スライドの第6章)の素材にはなり得るが、本設計の目的ではない
- 出力は**呼ぶたびに計算するビュー**(`status --view uncertainty`)。優先順位は要件や仮説の状態が変わるたびに変わる計算結果であり、保存すると陳腐化の管理が要るため。**生成物の型を新設するか `comparison` を使うか**という未決事項(medo-phase2-design.md §6-3)の答えは「どちらでもない」とする

## 2. 方式の選択

| 案 | 内容 | 判断 |
|---|---|---|
| **A(採用)** | 決定論の結びつき + fermi による感度・切り替え点の計算 + Jev の分類で並べるビュー | 計算できる部分(数値の振れ)はコードが計算し、計算できない意味の判断だけを Jev に任せる。knowledge-digest と同じ分担 |

## 3. 考え方

### 3.1 決め手の仮説(1つ決まると他が決まる)

**v1 は仮説だけでグラフを作る**。未確定事項は課題や fermi へのリンクを持たず(`OpenQuestion` の `scope` は core / secondary / out の区分であって課題を指さない)、候補の組を決定論で作れないため。未確定事項は §3.4 の分類だけで並べる。

- 節点: `status` が `unvalidated` / `validating` の仮説
- **候補の組**(決定論): 同じ fermi 推定に結びつく(`fermi_ref.artifact_id` が同じ)/ 根拠の課題が重なる(`challenge_ids` の共通部分がある)。全組み合わせは聞かない
- **辺**: 候補の組について、向きごとに Jev の `implies`(§5)を聞く。`determines`(A が確定すると B も決まる)と `narrows`(大きく絞られる)を区別する
- **波及範囲**: `determines` の辺だけをたどって到達できる節点の数。`narrows` は推移的とは限らないので、直接の辺の数だけを別に返す。循環(強連結成分)はひとまとまりとして数え、自分自身は数えない
- **Jevが使えないときの波及範囲は「不明」(null)**。同じ課題・同じ推定への所属は「解消すると他も決まる」ことを意味しないので、決定論の結びつきで代用しない

### 3.2 策を分けるパラメタ(明示する)

策の選択を分けるパラメタは、**名前の一致で推測せず、mini-prfaq に明示する**。同じ変数名でも策ごとに意味や尺度が違うことがあり、逆に名前が違っても同じ量を指すことがあるため。

- mini-prfaq に `pivot`(パラメタの表示名)と、策ごとの対応する変数名を持たせる(§4.1)
- 対応する変数は、**すべての策の fermi で仮定(`assume`)でなければならない**。また、**同じ量・単位・尺度**でなければならない(利用率を 0.3 と書く策と 30 と書く策を同じ探索値で置き換えると壊れる)。尺度の一致はコードで確かめられないので、`pivot_unit`(パラメタの単位)を明示させ、Skill の義務とする(§7)。ファクト参照(`fact`)は出典に縛られた値であり、不確実性の対象にしない
- 仮説の `fermi_ref` がこの変数を指していれば、その仮説を「切り替え点に結びつく仮説」とする

### 3.3 感度と切り替え点

**探索範囲**: mini-prfaq に `pivot_range`(下限・上限)が明示されていればそれを使う(利用率なら 0〜1 のように意味のある範囲を与えられる)。明示範囲は有限で下限 < 上限であることを保存時に検査し、下限が正なら対数刻み、そうでなければ線形刻みにする。無ければ、各策の仮定値の最小と最大から作る。すべて正なら [最小/10, 最大×10] を対数刻みで、0 や負を含めば [最小 − 幅, 最大 + 幅](幅 = 最大 − 最小、0 なら絶対値の最大か 1)を線形刻みで、それぞれ200点に区切る。

**感度**: 各策の推定値を、探索範囲の格子点で計算した最大と最小の差(振れ幅)。基準の推定値の**絶対値**に対する比も返すが、基準値が 0 なら比は返さない(null)。

**切り替え点**: 格子点で、推定値の最も高い策(最上位)が入れ替わる隣り合った2点を見つけ、その区間を**最上位がどれかを判定しながら**二分法で区間幅が相対 1e-3 になるまで詰める(フェルミ推定は桁感なので細かい精度は要らない)。2策の差の符号で詰めると、3策のとき最上位でない策どうしの交点を拾ってしまうため、常に全策を評価する。

- **不連続の判定**: 詰めた区間の両端で、いずれかの策の推定値そのものが大きく跳ぶ(絶対誤差 1e-9、または相対 1e-2 を超える)なら、切り替え点ではなく**不連続**(0除算の近くなど)として返す。どちらとも決めきれない(区間をこれ以上詰められない)場合は**判定不能**として返し、不連続と区別する
- 推定の計算が失敗する格子点は除き、除いた範囲を返す。失敗点をまたぐ区間では二分法を行わない
- 格子は有限なので、**結果は近似である**。入れ替わりが見つからなければ「調べた範囲の格子点では常に <策> が上」と返し、「全域で優位」とは言わない

**条件付きの問い**: 切り替え点は、他の仮定をすべて今の値に固定して求めたものである。出力には固定した仮定(変数名と値)を含め、問いを「他の仮定が今のままなら、<パラメタ> は <値> 以上か」と条件付きで示す。

**比べてよい推定**: `FermiModel` に任意の `unit`(推定値の単位、例: `万円/年`)を足す。**策どうしの `unit` が同じで空でないときだけ**切り替え点を計算する。KPI の目標値(`kpis[].target_value`)との比較も、KPI の `unit` と同じときだけ行う。推定値は「大きいほど良い」とする(費用のように小さいほど良い量は、策の fermi で効果から費用を引いた形に書く)。

### 3.4 未確定事項と、fermi に結びつかない仮説

Jev の `decision_relevant`(解消したら策の選択が変わり得るか)と `effort`(確かめる手間)だけで並べる(§5)。

## 4. スキーマ

### 4.1 mini-prfaq の策とパラメタ

**新しい生成物の型は作らず、既存の `mini-prfaq`(打ち手の候補セット)に乗せる。**

```python
class OptionMeta(BaseModel):
    name: str
    approach_type: str = ""
    tier: Literal["", "main", "sub", "matsu", "take", "ume"] = ""
    fermi: str = ""            # その策の推定(fermi-vN)
    pivot_variable: str = ""   # その策の fermi で、策を分けるパラメタに対応する変数名

class Artifact(...):
    ...
    pivot: str = ""                          # 策を分けるパラメタの表示名(mini-prfaq のみ)
    pivot_unit: str = ""                     # パラメタの単位(対応する変数はすべてこの尺度)
    pivot_range: tuple[float, float] | None = None
```

**CLI**: 既存の `--options "名前:手法の型"`(最初のコロン以降を手法名として受ける)は**変えない**。新しい項目は別のオプションで足す(手法名にコロンを含む既存の使い方を壊さないため)。

```
--tier "<名前>=<main|sub|matsu|take|ume>"       (繰り返し可)
--option-fermi "<名前>=fermi-vN"                 (繰り返し可)
--pivot "<パラメタ名>" --pivot-unit "<単位>" --pivot-var "<名前>=<変数名>"  (--pivot-var は繰り返し可)
--pivot-range "<下限>,<上限>"
```

**検査**(保存の対象だけに行い、既存の保存データの読み込みでは行わない):

- 策が4つ以上なら拒否する(tier の枠が松竹梅の3つしかないスキーマの形の制約)
- tier の組は上限だけを検査する: `main` は1つまで、`sub` は2つまで、`matsu` / `take` / `ume` は各1つまで。`main`/`sub` の系と松竹梅の系を混ぜたら拒否する。足りない分(`main` だけ、`matsu` だけ等)は受け、診断に回す
- 新しいオプション(`--tier` / `--option-fermi` / `--pivot-var`)を使うときは、策の名前が一意であることと、同じ策への重複指定が無いことを検査する
- `--tier` / `--option-fermi` / `--pivot-var` の `<名前>` が `--options` に無ければ拒否する
- `pivot` を指定したら、`fermi` を持つすべての策に `pivot_variable` が要る
- **策が1つでも保存は拒否しない**(不変条件6「診断は報告であって強制ではない」、7「寛容さはプロセスの層に」)。`uncertainty` ビューが「策が1つで比べられない」と返し、`status` の `actions` に `add_alternative_option` を出す。「最低2つ」は Skill の義務とする(§7)

`fermi` の参照先が無い、型が `fermi` でない、中身がモデルとして読めない、`pivot_variable` がその fermi に無いか `assume` でない、は**ビューの計算時に構造化したエラーとして項目ごとに返す**(保存時には fermi の中身まで検査しない。fermi は後から作り直されるため)。

### 4.2 `FermiModel` の `unit`

```python
class FermiModel(BaseModel):
    name: str
    variables: dict[str, FermiVar]
    formula: str
    unit: str = ""
```

既存の fermi(`unit` 無し)は空として読む。空の策を含む組では切り替え点を計算しない(§3.3)。

### 4.3 どの版と値を使うか

- mini-prfaq は、`status` と同じ規則で決まる**現在の版**(`_current_artifact_ids`)を使う
- 各策の fermi は、保存された結果ではなく**今のファクトでモデルを計算し直す**(仮定値を差し替えて繰り返し計算するため)。参照したファクトの `unverified_facts` / `doubtful_facts`(出典検証)と、fermi・mini-prfaq の stale を出力に含める

## 5. Jevに聞くこと

数値には触れず、関係と性質の分類だけを聞く(原則1)。

| 質問 | 型 | 対象 | 目的 |
|---|---|---|---|
| `implies` | choice | §3.1 の候補の組(向きごと) | `determines`(A が確定すると B も決まる)/ `narrows`(B が大きく絞られる)/ `none`。決め手を見つける辺 |
| `decision_relevant` | noul | 有効な切り替え点に結びつかない項目(未確定事項、fermi に結びつかない仮説、パラメタに結びつくが切り替え点が無い・計算できない仮説) | 「これが解消したら、どの策を取るかが変わり得るか」 |
| `effort` | choice | すべての項目 | 確かめる手間(`ask` すぐ聞ける / `research` 調査が要る / `experiment` 実証が要る) |

`state` には項目の本文、結びつく課題、策の名前と tier を渡す。`implies` は choice の確信度が閾値以上のときだけ辺にする(閾値は評価セットで決める。現在は 0.5。tune で `none` に辺を張る率が1割以下となる最小値を 0.50〜0.95、0.05刻みで選ぶ。今回の tune では 0.50〜0.65 の判定は同じで、その範囲では閾値を識別できない。評価記録: `scripts/eval/implies_results.md`)。

## 6. 並べ方と出力

### 6.1 並べ方(決定論)

重みづけの足し算はせず、上から順に比べる(重みの値そのものが根拠のない数値になるため)。

1. **有効な切り替え点**に結びつく(確かめれば進む策が決まる)。パラメタに結びつくだけで切り替え点が無い・計算できない仮説はここに入らない
2. 波及範囲が大きい。「対象外」(未確定事項)と「不明」(Jevなし)は出力で区別し、並べるときはどちらも既知の値の後ろに置く
3. 結びつくパラメタの振れ幅の比が大きい(null は後ろ)
4. `decision_relevant` が 0.5 以上
5. 手間が小さい(`ask` < `research` < `experiment`、null は後ろ)
6. 最後は ID 順(`hyp-N` → `oq-N`、番号の昇順)。同じ入力から必ず同じ順序になるようにする

### 6.2 出力 `medo status --view uncertainty`

json と digest の両方を返す。全体に `judge`(`ok` / `unavailable`)、mini-prfaq の現在の版、策の一覧(名前・tier・推定値・単位)、`pivot` と探索範囲、切り替え点、固定した仮定、stale・未検証の参照を持つ。項目ごとに次を持つ。

| フィールド | 内容 |
|---|---|
| `id` / `kind` | 項目のID(`hyp-N` / `oq-N`)と種類 |
| `keystone` | 波及範囲(`determines` をたどった数。未確定事項は `not_applicable`、Jev が無ければ `unknown`)、`narrows` の直接の数、辺の根拠 |
| `pivot` | 切り替え点に結びつくか |
| `swing` | 結びつくパラメタの振れ幅と比 |
| `ask` | 確かめるべき問い(条件付き。「他の仮定が今のままなら、<パラメタ> は <値> 以上か」) |
| `decision_relevant` / `effort` | Jev の分類 |
| `errors` | 計算できなかった理由(§6.3) |

### 6.3 計算できない場合

推測で補わず、理由と一緒に返す。

| 状況 | 扱い |
|---|---|
| mini-prfaq が無い | ビュー全体で「打ち手の候補が無い」 |
| 策が1つ | 「策が1つで比べられない」。`actions` に `add_alternative_option` |
| `pivot` が無い、策に fermi が無い、`unit` が揃わない | 切り替え点は計算しない。理由を返す |
| fermi の参照・中身・`pivot_variable` が不正、または一部の策の計算が失敗する | その策について構造化したエラーを返し、**全策の比較(切り替え点)は計算しない**。残りの策だけの比較は v1 では返さない(全体の判断を誤らせるため) |
| 格子点で入れ替わりが無い | 「調べた範囲の格子点では常に <策> が上」(近似) |
| 入れ替わる区間で策の値が跳ぶ | 「不連続」として返し、切り替え点に数えない。決めきれなければ「判定不能」 |
| 計算が失敗する格子点 | 除いた範囲を返す |

### 6.4 Jevが使えないとき

既存の `research triage` / `knowledge dedupe` とそろえる。

- `TYPESAFE_API_KEY` が無い: 決定論の部分(感度・切り替え点)だけを `judge: unavailable` 付きで返す。波及範囲・`decision_relevant`・`effort` は null(終了コード0)
- 鍵があるのに呼び出し・解析が失敗した: 非ゼロ終了し `error:` を出す

## 7. Skill

- `medo-propose-options`: 策を**最低2つ・最大3つ**作る。メインとサブ(3つなら松竹梅)の tier、策ごとの fermi(`unit` を付け、仮定には根拠のメモを付ける)、策を分けるパラメタ(`--pivot` / `--pivot-unit` / `--pivot-var`、意味のある範囲があれば `--pivot-range`)を付けて保存する。**対応する変数は、すべての策で同じ単位・尺度で書く**
- `medo-decide`: 振り返りで `medo status --project <id> --view uncertainty` を読み、最上位の「確かめるべき問い」をユーザーへの返答の中で示し、次の周回の焦点(`focus_hypothesis`)にするかを尋ねる。最上位が未確定事項(`oq-N`)なら、まず仮説にして要件に保存してから焦点にするよう案内する。80行の上限内に収める

## 9. テストと評価

- 決定論のユニットテスト:
  - 切り替え点: 単調な式、単調でない式、近い2つの交点(格子で取り逃しうることを近似として扱う)、不連続(`1/(x-1)`)、入れ替わりが無い、計算失敗点を含む
  - 探索範囲: 明示あり、すべて正(対数)、0・負を含む(線形)
  - 感度: 基準値0で比が null
  - 波及範囲: `determines` だけをたどる、`narrows` は直接の数、循環、Jev なしで null
  - 並べ方: §6.1 の順
  - 検査: 策4つ・tier の混在・名前の不一致・`pivot` の対応漏れを拒否、策1つは受ける、既存の mini-prfaq(新フィールド無し)と既存の fermi(`unit` 無し)を読める
- Jev は既存のテストと同じく差し替える。鍵なしで `judge: unavailable`、失敗で非ゼロ終了
- **正解付きの評価セット**(`scripts/eval/` に置く): `implies` の組(`determines` / `narrows` / `none` の正解付き)を調整用と検証用に分ける。受け入れ条件は検証用の組で、`none` の組に辺を張る率が1割以下、`determines` の組の8割以上を `determines` と判定する(評価前に固定)

## 11. やらないこと

- **生成物として保存する**: 呼ぶたびに計算する(§1)
- **重みの足し算による総合点**: 根拠のない重みを作らない(§6.1)
- **ファクト参照の変数を動かす**: 出典に縛られた値は不確実性の対象にしない
- **名前の一致によるパラメタの推測**: 策を分けるパラメタは明示する(§3.2)
- **複数のパラメタを同時に動かす切り替え点**: v1 は1つのパラメタだけを動かし、他は固定して条件付きで示す
- **推定ごとの良し悪しの向き**: v1 は「大きいほど良い」に揃える
- **策が4つ以上**: 最大3つ(松竹梅)
- **未確定事項のグラフ**: 課題へのリンクが無いため v1 は仮説だけ(§3.1)
- **顧客向けロードマップの生成**: 最終提案スライドの第6章の素材にはなり得るが、本設計では扱わない
