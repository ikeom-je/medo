## 1. 目的

フェーズ1は「What/Whyの合意形成」の縦切りを通した。フェーズ2は、その合意形成を**利用者が漏れなく重複なく進められるよう導く**支援に踏み込む。

**medoの位置づけ**: 利用者を導く支援ツールであり、判断を代行しない。フレームワークをパターンとして整理し、MECE(漏れなく重複なく)なヒアリングを支える。

---

## 2. 不変条件

フェーズ2の設計変更で**変えてはならない**もの。

1. **数値・事実の通り道にLLMを挟まない**(product.md 原則1)。保存済みの値の参照・計算・鮮度判定はコードが行う
2. **課題も要件も最初から確定しない**(原則3)。確度は `confidence` で表し、進行制御(ゲート)で表さない
3. **自律的なmulti-agentを採らない**(差別化軸)。会話Agentは1体(ホストLLM)+決定論的ツール群
4. **medoはコマンドラインツールである**。Skillは手順書であり、実行主体は常にホストLLM。medo自身はAgentにならない
5. **認証・マルチテナントを導入しない**(利用スコープは本人のみ)
6. **診断は報告であって強制ではない**。未接続・未確認・未解決を検出しても保存を拒否しない

---

## 3. 標準周回(4ステージ)

暗黙知は**AsIsとToBeを何度も往復して初めて出てくる**。往復は頭の中では回らず、**各ステージで成果物を出し、レビューし、顧客にぶつけて反応を得る**ことで進む。

```
┌─────────────────────────────────────────────────┐
│  1. Investigate & Draft   調べる・仕立てる        │
│     公開情報と顧客情報を集め、現状を整理して出す   │
│                      ↓                          │
│  2. Internal Review       内部検証               │
│     論理矛盾・GAP・欠落を洗い出し論点を研ぐ        │
│                      ↓                          │
│  3. Client Dialogue       ぶつける・反応を得る     │
│     顧客に共有し、確認・共感・異議を記録する        │
│                      ↓                          │
│  4. Adapt & Decide        振り返る・次へ進む       │
│     反応を要件に反映し、往復継続か次段階かを判断    │
└──────────────────┬──────────────────────────────┘
                   └──▶ 1へ戻る(収束するまで)
```

**これは固定の状態機械ではなく「標準的な1周」である**。利用者がどのステージから始めても成立する(判断2)。順序を強制せず、CLIは現在地だけを返す。

**当初案の7ステップから4ステージへ集約した**(相互レビュー)。成果物出力や内部フラグ操作まで分解すると、実務者が記憶して回すには粒度が細かすぎる。日常的に意識できるのは3〜4が限界である。

### ステージとコンポーネントの対応

| Stage | 主な入力 | 保存するもの | 主なCLI操作 | 次の判断材料 |
|---|---|---|---|---|
| **1. Investigate & Draft** | 公開情報・顧客の生の声・提供資料 | `facts` / `RequirementsDoc.as_is` / `research` / `as-is-report` | `facts save` / `requirements save` / `artifacts save` | `model.coverage` |
| **2. Internal Review** | 最新の `as-is-report` | `AsIsReportReviewed` イベント | `medo review add` | `workflow.review` |
| **3. Client Dialogue** | `as-is-report` とそのスライド | `slides` / `StakeholderResponded` イベント | `artifacts save` / `medo respond add` | `workflow.responses` |
| **4. Adapt & Decide** | レビュー所見・顧客の反応 | 要件の新版 / `ToBeCheckpointRecorded` イベント | `requirements save` / `medo checkpoint answer` | `readiness` / `actions` |

各ステージは `medo status` の該当ブロックだけを読めば進められる(詳細: [status契約](phase2-status-contract.md))。

### 周回ごとに検証論点を1つ定める

**何を検証すれば仮説が前進・棄却するかを事前に決める**。周回ごとに `focus_hypothesis_id` を1つ選び、その周回の顧客対話はそれを検証することに集中する。

これが無いと、蓄積した課題とGAPすべてに一律で向き合うことになり、周回が発散する。Lean Startupのbuild-measure-learnが実験前に検証基準を定めるのと同じ考えである([The Lean Startup](http://theleanstartup.com/principles))。

## 4. 主要な設計判断

詳細な根拠は各詳細ファイルにある。ここでは判断とその一行理由のみを置く。

| # | 判断 | 理由 | 詳細 |
|---|---|---|---|
| 1 | フレームワークに基づく**固定スキーマ**を持つ(汎用ノード+タグにしない) | 項目が定義されていなければ「何が漏れているか」を機械的に指摘できず、MECEを担保できない | [domain](phase2-domain-model.md) |
| 2 | **順序は固定しない**。CLIが充足状況を返し、Skillが次の問いを決める | 実案件は典型パターンに従わない。理想像から語り始めることも、制約から入ることもある | [status](phase2-status-contract.md) |
| 3 | **顧客に問う項目とSkillが下書きする項目を分ける** | 顧客はGAPと真因の区別に沿って話さない。空欄を機械的に埋めようとすると穴埋め尋問になる | [domain](phase2-domain-model.md) |
| 4 | **AsIsとToBeを往復させて暗黙知を引き出す**。ゲートを設けない | 仮のToBeは実態を引き出すプローブ。AsIsの薄さはToBeを止める理由ではなく確度を `assumed` に留める理由 | [workflow](phase2-workflow-model.md) |
| 5 | 往復は**出力→レビュー→共有→反応**で回す | 往復は頭の中では回らない。成果物と反応がないと暗黙知は出てこない | [workflow](phase2-workflow-model.md) |
| 6 | 要素間の**リンクは任意**。未接続はエラーにしない | 痛みは明確だが理想像が未言語化、という状態は実案件で普通に起きる | [domain](phase2-domain-model.md) |
| 7 | **解像度は `confidence` が制御する** | 知らない顧客情報は仮説。スキーマを粗くするのではなく確度で表す | [domain](phase2-domain-model.md) |
| 8 | **GAP(現象)とボトルネック(真因)を分離する** | 現象の差分をそのまま課題と呼ぶと対症療法しか出ない | [domain](phase2-domain-model.md) |
| 9 | **未検証の真因は仮説に一元管理する** | 確定した真因と未検証の仮説を二重に持つと整合が崩れる | [domain](phase2-domain-model.md) |
| 10 | **進行記録は要件と分けてイベントとして持つ** | 要件は保存のたびに版が進むため、反応やレビューを要件内に置くと記録した瞬間に旧版宛てになる | [workflow](phase2-workflow-model.md) |
| 11 | **収束判断は「現在の対象」に対してのみ行う** | 旧版への異議で永久に止まる、古い合意で誤って通る、の両方を防ぐ | [workflow](phase2-workflow-model.md) |
| 12 | **サブエージェント機構に依存しない** | Claude CodeのTask相当がCodex/agyに無い。Skill+CLIだけで「モデルを変えて実行する」を実現する | [portability](phase2-skill-portability.md) |

## 5. フェーズ2の実装順序

| 優先度 | 項目 | 備考 |
|---|---|---|
| **1** | ドメインモデル + ID規約 + 移行 + `model` 診断 | ID採番シーケンス・型付きリンク・スコープ属性を含む。これが無いと2を開始できない |
| **2** | 陳腐化のセクション単位化 + カバレッジ + 2段階重大度 | 1と密結合。飛ばすと全生成物が常時stale化して破綻 |
| **3** | 出典検証の強化(URLフェッチ + 数値突合) | **他と技術的に独立しており並行可能**。フェーズ1 Task10で穴を実証済み |
| **4** | ワークフローイベント + 収束規則 + `workflow`/`readiness` 診断 | ステージ2〜4の基盤 |
| **5** | 生成物の依存グラフ + stale伝播 | スライド生成の前提 |
| **6** | `research` / `as-is-report` 生成物 + Skill 4本 | 標準周回を回せる最小構成 |
| **7** | スライド生成(AsIs説明 / 最終提案) | 利用者の主要求 |
| **8a** | ナレッジ来歴スキーマ(`supersedes`・不変保存) | 8bの前提。統合でIDが変わると過去の引用が全滅する |
| **8b** | `knowledge-digest`(LLMによる統合提案) | 統合後も旧entryを残し、過去の引用が検証可能であること |
| **9** | `decision-roadmap`(再定義。感度分析と連動) | `Hypothesis.fermi_ref` が前提 |
| 後続 | `build-mock` / `propose-architecture` / pricing(再定義) / 簡易Webアプリ | 下記の完了定義の改訂が必要 |

### 相互レビューで訂正された当初案の誤り

- **pricing計算機の削除は誤り**: 「クラウド非依存」は「料金を扱わない」ことを意味しない。不正だったのはテスト方針(単一の公式Calculatorを正解に置けない)であり機能の要否ではない。**再定義して後送り**
- **簡易Webアプリの除外根拠が誤り**: 正本 `medo-design.md` はフェーズ2に明記しており、差別化軸の「単一のWebアプリに閉じる」は「Webアプリを作らない」という意味ではない。**優先度を下げるが除外しない**

### フェーズ2完了定義の改訂(要承認)

現行は「課題→What/Why合意→スライド+モックまで半日」だが、`build-mock` を後続に送るため改訂が必要:

> **改訂案**: 課題→標準周回による現状と理想の合意(収束判定を満たす)→共感できるドキュメント+提案スライドまで半日。knowledgeが案件を跨いで洗練される。
